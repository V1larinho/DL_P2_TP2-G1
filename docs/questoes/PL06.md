## Q1 — Relação entre Dice e IoU

**Pergunta:** Se IoU = 0,6, qual é o valor de Dice?

**Resposta:**

A relação entre Dice e IoU é:

$$\text{Dice} = \frac{2 \cdot \text{IoU}}{1 + \text{IoU}}$$

Substituindo IoU = 0,6:

$$\text{Dice} = \frac{2 \times 0{,}6}{1 + 0{,}6} = \frac{1{,}2}{1{,}6} = \mathbf{0{,}750}$$

**Resposta: Dice = 0,750**

> [!NOTE] A relação inversa é IoU = Dice / (2 − Dice). Ambas as métricas concordam em ordenação mas o Dice é sempre ≥ IoU para valores em ]0,1[, o que torna as comparações entre artigos menos diretas sem converter.

## Q2 — Segmentação de pólipos (3% da imagem): pixel accuracy vs Dice

**Pergunta:** Numa segmentação de pólipos que ocupam apenas 3% da imagem, calcula a pixel accuracy e o Dice do modelo "sempre fundo". O que concluis?

**Resposta:**

| Métrica | Modelo "sempre fundo" | Interpretação |
|---|---|---|
| **Pixel accuracy** | **0,97 (97%)** | Parece excelente — mas o modelo nunca encontra o pólipo |
| **Dice** | **0** | TP = 0 → numerador = 0 → Dice = 0 |

**Cálculo do Dice:**

$$\text{Dice} = \frac{2 \cdot \text{TP}}{2 \cdot \text{TP} + \text{FP} + \text{FN}}$$

Como o modelo prevê sempre "fundo": TP = 0, FP = 0, FN = todos os píxeis de pólipo.

$$\text{Dice} = \frac{2 \times 0}{2 \times 0 + 0 + \text{FN}} = 0$$

**Conclusão:** A pixel accuracy é **inadequada para classes muito desequilibradas**. Um classificador trivial que nunca detecta a classe rara atinge 97% de accuracy. O Dice/IoU por classe penaliza corretamente a ausência de deteção, sendo a métrica apropriada nestes cenários.

> [!IMPORTANT] Este é o mesmo problema do nosso dataset CODEBRIM: a eflorescência aparece em apenas ~11% dos recortes. Daí usarmos Macro-F1 (que trata todas as classes igualmente) e não accuracy.

## Q3 — Unidade de agrupamento do CODEBRIM

**Pergunta:** Qual é a unidade de agrupamento do nosso dataset (CODEBRIM)? O que acontece se for ignorada?

**Resposta:**

A unidade de agrupamento do CODEBRIM é a **imagem de origem** (da qual os recortes foram extraídos). O dataset contém 7 677 recortes provenientes de 1 522 imagens de 30 pontes.

**Regra:** recortes da mesma imagem de origem têm de ficar **todos na mesma partição** (treino, val ou teste). A divisão é feita por imagem, não por recorte.

**O que acontece se for ignorada:**

1. Recortes quasi-duplicados (mesma textura, mesma iluminação, mesmo ângulo, apenas posição ligeiramente diferente na imagem) ficam distribuídos por partições diferentes.
2. O modelo vê em treino patches muito semelhantes aos de validação/teste → **fuga de dados**.
3. As métricas de validação e de teste ficam **artificialmente otimistas** — o modelo aparenta generalizar melhor do que realmente generaliza.
4. A comparação justa entre estratégias AL fica comprometida: a corrida com seed que "acertou" mais quasi-duplicados no treino ganha injustamente.

**No nosso projeto:** `data/splits.csv` foi construído com agrupamento por `image_id`; verificado com `scripts/contar_codebrim.py` — 0 imagens em duas partições.
